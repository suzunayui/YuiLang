# ネイティブコンパイルの設計

`yui build` が、インタプリタを含まない実行ファイルを直接書き出すようにするための設計です。
1〜9 節は実装前に書いた設計で、そこにある数字は見積もりです。実装した結果と実測は 10 節以降にあります。

## 1. 何を解決するか

現在の実行方式には、作りから来る上限が2つあります。

- **速度**: 値に型の印（24バイト）を付けて動かし、機械語にできない操作はインタプリタへ戻します。
  個別の操作を機械語に置き換えていく改良は効きが悪くなってきました
  （フィールド読み出し・定数・文字列比較を機械語にしても、YuiLang 版の構文解析は 45ms → 40ms）。
- **大きさ**: `yui build` の出力は処理系を丸ごと含むので約 0.9MB で、プログラムの大きさに関係しません。
  処理系が Rust 製なので、Rust の最小の実行ファイル（約 200KB）より小さくはなりません。

型はコンパイル時にすべて分かっています。それを使い切れば、印も、インタプリタへの往復も、
処理系の同梱も不要になります。

## 2. 目標と、目標にしないこと

目標:

- 整数ループとリスト処理で Rust の 1〜1.5 倍以内。
- 小さなプログラムの実行ファイルが数十 KB。
- 実行結果・エラーメッセージ・終了コードが、今の `yui run` と完全に同じ。

目標にしないこと（少なくとも最初は）:

- `yui run` と `yui test` の置き換え。これらは今のインタプリタと JIT のまま残します。
  起動が速く、エラー時の情報も多いためです。
- Rust を常に上回ること。上回れるのは、副作用のない関数の結果再利用のように、
  Rust が自動では使えない保証を使える場面に限られます。

## 3. 全体の流れ

```
ソース → 構文解析 → 型チェック → 型付き中間表現 → 単相化 → 機械語 → 実行ファイル
                                 （新規）        （新規） （新規）  （新規）
```

- **型付き中間表現**: 型チェッカは今、整数の変数など一部の型しか外へ渡していません。
  すべての式の型を渡すようにし、それをもとに「コピー」「解放」を明示した単純な命令列に落とします。
- **単相化**: `fn id<T>(x: T)` は、使われた型ごとに別の関数として機械語にします。
  値の大きさと後始末の方法が型ごとに決まるので、実行時に型を調べる必要がなくなります。
- **機械語**: レジスタ割り当てを行い、今の JIT のアセンブラ（`src/jit.rs` の `Asm`）を使って出力します。

## 4. 値の持ち方

| 型 | 持ち方 |
| --- | --- |
| `Int`, `Float` | 8 バイトをそのままレジスタやスタックに置く |
| `Bool` | 1 バイト（レジスタ上では 0 か 1） |
| `Unit` | 何も持たない |
| `String`, `List<T>`, `Map<K, V>`, クロージャ | ヒープ上のブロックへのポインタ。先頭に参照カウント |
| `struct` | ヒープ上のブロックへのポインタ。フィールドを順に並べる |
| `enum`, `Option`, `Result` | 番号と中身。中身のない列挙は整数 1 個 |

- 型の印は持ちません。どの位置に何の型があるかは、コンパイル時に決まっています。
- `List<Int>` は 8 バイトの並び、`List<Bool>` は 1 バイトの並びのように、要素型ごとに詰めます。
  今の「実行時に整数だけか調べて詰める」処理は不要になります。
- メモリ管理は今と同じ参照カウントです。値セマンティクスなので循環は起きません。
  所有者が 1 人のときにその場で書き換える最適化も、今と同じ考え方で入れます。

## 5. 実行時部品

実行ファイルに同梱する最小限の部品です。プログラムが使うものだけを入れます。

- メモリの確保と解放
- 文字列（連結、比較、切り出し、検索、数値との変換）
- リストと `Map`
- 入出力（標準出力、標準入力、ファイル、コマンドライン引数）
- エラー終了（メッセージとソース位置の表示）

**これを何で書くか**が最大の設計判断です。

| 案 | 長所 | 短所 |
| --- | --- | --- |
| A. YuiLang で書く（低レベル操作の組み込み関数を数個だけ追加） | 同じコンパイラで機械語になる。セルフホストと方向が一致。使わない部品を自然に省ける | 生のメモリを触る機能が言語に入る（実行時部品のファイルだけに許す） |
| B. Rust で書いて機械語の塊として埋め込む | 書くのは速い | Rust の標準ライブラリを避ける必要があり、結合の仕組みを自作することになる。大きさも読みにくい |
| C. アセンブラで手書き | 最小 | 量が多く、検証が難しい |

**A を推奨します。** 小数の文字列化や `Map` のような込み入った部品を、検査の効く言語で書けます。

## 6. 実行ファイルの書き出し

OS ごとにファイル形式が違うので、順に対応します。

1. **Windows x64（PE）**: 開発機なので最初。OS の機能は kernel32 の関数を取り込んで呼びます。
2. **Linux x64（ELF）**: 外部ライブラリなしで、システムコールを直接呼びます。
3. **macOS**: Intel は 2 の応用で済みますが、Apple Silicon は ARM64 用の機械語生成が丸ごと必要です。
   署名も必要です。優先度は最後にします。

対応していない OS や、まだ対応していない言語機能を使うプログラムでは、
`yui build` は今の方式（処理系を同梱）に自動で切り替えます。使う側から見て壊れることはありません。

## 7. 段階

各段階の終わりに、全テストが通り、対応済みのサンプルが今の実行方式と同じ結果になることを条件にします。

| 段階 | 内容 | 終了条件 |
| --- | --- | --- |
| 1 | 型チェッカがすべての式の型を渡す。型付き中間表現と単相化 | 既存の動作は変えない。中間表現を表示して確認できる |
| 2 | Windows の実行ファイル書き出し。整数・真偽値・関数・ループ・`print`（整数と文字列定数）だけ | `fib` と整数ループが単体の実行ファイルとして動く。大きさと速度を実測 |
| 3 | 文字列、リスト、参照カウント、文字列補間、実行時エラーの表示 | リストのベンチマークが動く |
| 4 | 構造体、列挙、`match`、`Option` / `Result`、`?`、クロージャ | `examples/` の大半が動く |
| 5 | `Map`、残りの標準メソッド、ファイル入出力、引数、契約 | `examples/` がすべて同じ結果になる |
| 6 | Linux、続いて macOS | 各 OS の CI で確認 |
| 7 | `yui build` の既定をネイティブに切り替え | 未対応の場合は自動で今の方式に戻る |

段階 2 が終わった時点で、狙った速度と大きさが本当に出るかを実測できます。
出なければ、そこで設計を見直します。それより先へ進む前の判断点です。

## 8. 正しさの確かめ方

- **突き合わせテスト**: 同じプログラムを今の実行方式とネイティブの両方で動かし、
  標準出力・エラーメッセージ・終了コードが一致することを全サンプルで確認します。
  今の JIT と VM の突き合わせと同じやり方です。
- **エラーケース**: `tests/errors/` の実行時エラー（オーバーフロー、範囲外、契約違反など）も対象にします。
- **メモリ**: 確保と解放の回数を数える検査用のビルドを用意し、終了時に一致することを確認します。

## 9. 危険と不確かな点

- **量が多い**: 段階 3〜5 が本体で、実行時部品と機械語生成の両方を新しく書きます。
  今の JIT（約 2,000 行）より大きくなります。
- **実行方式が 2 つになる**: インタプリタ（`yui run`）とネイティブ（`yui build`）で挙動がずれる危険があります。
  突き合わせテストで防ぎます。
- **小数の文字列化**: Rust の標準ライブラリと同じ結果を出す必要があり、専用のアルゴリズムの実装が要ります。
- **不具合の調査が難しくなる**: ネイティブの異常終了は、今のようにエラーコードと位置では出ません。
  検査用のビルドを用意して補います。
- **速度の見込み**: 「Rust の 1〜1.5 倍」は、型の印とインタプリタへの往復がなくなることからの見積もりです。
  レジスタ割り当ての質が Rust（LLVM）に及ばない分は残ります。

## 10. 段階 2 の実測結果（2026-11-25、Windows x64）

`yui build --native` として実装しました（`src/jit/native.rs`）。対象は `Int` と `Bool` だけを使う
プログラムで、それ以外は「未対応」として断ります。段階 1（型チェッカがすべての式の型を渡す）は、
この範囲では不要なので後回しにしています。

| | Rust | `--native` | `yui run`（JIT） |
| --- | --- | --- | --- |
| `fib(38)` の時間 | 60 ms | 172 ms | 4 ms（結果の再利用あり） |
| 整数ループ 3 億回の時間 | 148 ms | 298 ms | 293 ms |
| 実行ファイルの大きさ | 227,840 バイト | 2,560 バイト | — |

- **大きさ**: 狙いどおりです。Rust の約 90 分の 1 になりました。
  出力の多いプログラムでは、エラーメッセージの文字列が大半を占めます（`tests/native/values.yui` で約 25KB）。
- **速度**: 狙い（Rust の 1〜1.5 倍）には届いていません。整数ループは今の JIT と同じです。
  今の JIT はすでに整数をレジスタに置いているので、型の印をなくしても、このループでは差が出ませんでした。
  残りの差は、割り算を使う判定の工夫や無駄な転送の削減など、最適化の質の差です。
- **`fib`**: 結果の再利用（JIT にはある）をまだ入れていないので、`yui run` より遅くなっています。
- **正しさ**: `tests/native/` の 9 本で、出力・エラーメッセージ・終了コードが `yui run` と一致します。

つまり、この方式が確実にもたらすのは「大きさ」と「インタプリタへの往復がなくなること」で、
整数だけの計算の速度は、方式ではなく最適化の作り込みで決まります。
文字列・リスト・構造体を使う処理（今は Rust の約 5 倍）で効果が出るかは、段階 3 以降で確かめます。

## 11. 決めたこと（2026-11-25）

1. 実行時部品は YuiLang で書く（案 A）。生のメモリを触る組み込み関数が、限定つきで言語に入ります。
   段階 2 の出力とエラー表示の部品だけは、量が少ないので機械語で直接書いてあります。
2. 最初の対応は Windows x64 だけに絞る。
3. 段階 2 の実測結果を見てから、先へ進むかを判断する。

## 12. 段階 3 の途中経過: 整数のリスト（2026-11-25、Windows x64）

段階 3 のうち、`List<Int>` と参照カウントまでを入れました。文字列と文字列補間は 13 節です。

| | Rust | `--native` | `yui run`（JIT） |
| --- | --- | --- | --- |
| リストのベンチマーク（300 万件を `push`、`map` → `filter` → `fold`） | 20.5 ms | 24.1 ms | 35.9 ms |
| 実行ファイルの大きさ | 229,888 バイト | 4,096 バイト | — |

- **速度**: Rust の約 1.2 倍で、狙い（1〜1.5 倍）に入りました。JIT より約 1.5 倍速くなっています。
  整数だけの計算と違い、リスト処理では型の印とインタプリタへの往復がなくなる効果が出ます。
- **大きさ**: リストを使わないプログラムは段階 2 と同じ 2,560 バイトのままです。
  リスト用の部品は、使うプログラムにだけ入ります。

入れたもの:

- **値の持ち方**: リストはヒープ上のブロックで、先頭から 8 バイトずつ `[参照カウント][長さ][容量][要素...]`。
- **所有の規則**: リストの変数は参照を 1 つ持ち、リストの式は参照を 1 つ作ります。
  変数がスコープを抜けるとき（`return` / `break` / `continue` を含む）と、代入で上書きされるときに手放します。
  関数に渡した引数は、呼ばれた側が手放します。
- **その場での追加**: `xs = xs.push(v)` は、`xs` がただ 1 人の持ち主で空きがあれば、関数を呼ばずにその場で足します。
  ほかに持ち主がいれば複製するので、値としての意味（片方を変えても他方は変わらない）は保たれます。
- **ループへの展開**: `map` / `filter` / `fold` / `any` / `all` にその場で書いたクロージャは、
  関数呼び出しにせず、ループの本体として機械語にします。
- **実行時部品**: `src/jit/runtime.yui` に YuiLang で書いてあり、利用側と同じコンパイラで機械語になります。
  このファイルの中でだけ、メモリを直接読み書きする組み込み関数（`__load` など 5 個）が使えます。
  メモリの確保と解放だけは、OS のヒープ関数を呼ぶ短い機械語です。
- **メモリの検査**: 環境変数 `YUI_NATIVE_CHECK_HEAP` を設定してビルドすると、確保したブロックを数え、
  `main` が終わった時点で残っていれば報告して終了コード 3 で終わる実行ファイルになります。
  `cargo test` の突き合わせテストは、すべてこの検査つきでビルドしています。

まだ対応していないもの（使うと「未対応」として断ります）: `Int` 以外を要素にするリスト、リスト同士の比較、
リストの表示、変数に入れた関数やクロージャを `map` などに渡すこと、`fold` の結果がリストになる場合、
上に挙げた以外のリストのメソッド。

## 13. 段階 3 の続き: 文字列（2026-11-25、Windows x64）

文字列と文字列補間を入れました。これで段階 3 の内容（文字列、リスト、参照カウント、補間、実行時エラーの表示）は
ひととおり入りましたが、リストの要素はまだ `Int` だけです。

| | Rust | `--native` | `yui run`（JIT） |
| --- | --- | --- | --- |
| 文字列のベンチマーク（200 万回、補間で文字列を作り、比較し、長さを数える） | 67.1 ms | 76.7 ms | 202.8 ms |
| 実行ファイルの大きさ | 114,688 バイト | 4,608 バイト | — |

- **速度**: Rust の約 1.15 倍、JIT の約 2.6 倍です。時間の大半は OS のメモリ確保と解放で、ここは Rust と同じものを使っています。
- **途中で分かったこと**: 最初の版は 134 ms でした。補間で作る文字列の初期容量を整数 1 個あたり 16 バイトと見積もっていて、
  整数の追記（最大 20 バイト）のたびにメモリを取り直していたのが原因です。埋め込む値の型から見積もるようにして解消しました。

入れたもの:

- **値の持ち方**: `[参照カウント][バイト数][容量][UTF-8 のバイト列]`。リストと同じ所有の規則で解放します。
- **定数**: 文字列リテラルは実行ファイルの中に置き、参照カウントを負にして「解放も書き換えもしない」印にしています。
  リテラルを使うだけならメモリの確保は起きません。
- **補間**: `"a {x} b"` は、必要な大きさを見積もって 1 回確保し、部品を順に書き足します。
  `print("...")` に直接書いた場合は文字列を作らず、部品ごとに出力します。
- **借用**: 変数が持っている文字列を比較・出力・メソッドに使うだけなら、参照カウントを触りません。
- **操作**: `==` `!=` `<` `<=` `>` `>=`、`len()`（文字数）、`is_empty()`、`contains` / `starts_with` / `ends_with`、
  `Int` / `Bool` / `String` の `to_string()`、任意の文字列の `print`。
- **使う部品だけ入れる**: 実行時部品は、呼ばれるものから辿れる関数だけを機械語にします。
  文字列を使わないプログラムに文字列の部品は入りません。

まだ対応していないもの: `trim` / `to_upper` / `to_lower` / `replace` / `slice` / `split` / `chars` / `codes` / `to_int`、
`List<String>`、`fold` の結果が文字列になる場合、`panic`。

## 14. 段階 4 の前半: 構造体・列挙・`match`（2026-11-25、Windows x64）

構造体、列挙（`Option` / `Result` を含む）、`match`、`?`、任意の要素型のリストを入れました。
クロージャを値として扱うこと（変数に入れる、関数に渡す）は、この次です。
`examples/hello.yui` が初めてネイティブで通り、`yui run` と同じ出力になります。

| | Rust | `--native` | `yui run`（JIT） |
| --- | --- | --- | --- |
| 構造体・列挙のベンチマーク（構造体 100 万個のリスト、列挙の生成と `match` を 200 万回、`Option` を 200 万回） | 15.2 ms | 36.7 ms | 416 ms |
| 実行ファイルの大きさ | 113,664 バイト | 6,656 バイト | — |

- **速度**: JIT の約 11 倍ですが、Rust の約 2.4 倍で、狙い（1〜1.5 倍）には届いていません。
  Rust は構造体や `Option<Int>` をヒープに置かずに値のまま扱いますが、この実装は 1 個ずつブロックを確保するためです。
  次の改善候補は、小さな列挙（`Option<Int>` など）と小さな構造体を確保せずに持つことです。
- **途中で分かったこと**: 最初の版は 89 ms でした。値 1 個ごとに OS のヒープを呼んでいたためで、
  64 バイト以下のブロック専用の確保器（大きさ別の空きリスト）を入れて 36.7 ms になりました。

入れたもの:

- **型の受け取り**: `--native` のときだけ、型チェッカがすべての式の型を渡します（設計の段階 1）。
  `yui run` や `yui check` は、これまでどおりこの処理を行いません。
- **値の持ち方**: すべての値は 8 バイト。構造体は `[参照カウント][フィールド...]` のブロック、
  列挙は `[参照カウント][番号][フィールド...]` のブロックです。フィールドのない列挙値（`None`、`Color.Red` など）は
  番号そのものを値にして、確保しません（4096 未満の数はアドレスにならないので区別できます）。
- **ジェネリックな型**: `Option<Int>` と `Option<String>` のように、型引数の組み合わせごとに別の型として扱います。
- **解放コードの自動生成**: 型ごとに「参照を 1 つ手放し、最後の 1 つなら中身も手放して解放する」機械語を、
  使われた型についてだけ生成します。
- **借用**: `for` の変数、`match` のパターンで付けた名前、クロージャの引数は、元のリストや値から借りるだけで、
  参照カウントを触りません（元の値は、その間ずっと保持されています）。
- **途中で抜ける場合の解放**: 式を組み立てている途中で `?` / `return` / `break` が外へ抜けるとき、
  そこまでに評価して保持している一時値を解放します。メモリ検査がこの漏れ（`Ok(a + f()?)` の形）を見つけました。
- **操作**: 構造体の生成とフィールド読み出し、列挙の生成、`match`（整数・文字列・真偽値・列挙の入れ子パターン）、`?`、
  `unwrap_or` / `is_some` / `is_none` / `is_ok` / `is_err`、リストの `get`、任意の型への `fold`。

まだ対応していないもの: 構造体・列挙・リストどうしの `==`、それらの表示（`"{p}"`）、
ジェネリックな関数、`requires` / `ensures`、`assert`、引数が 5 個以上の関数、`Float`、`Map`、
`Int` の `abs` などのメソッド。

## 15. 段階 4 の後半: 関数を値として扱う（2026-11-25、Windows x64）

クロージャと関数を、値として扱えるようにしました（変数に入れる、関数に渡す、関数から返す、構造体やリストに入れる、
`map` などに名前や変数で渡す）。これで段階 4 に挙げた言語機能はひととおり入りました。

| | Rust | `--native` | `yui run`（JIT） |
| --- | --- | --- | --- |
| クロージャのベンチマーク（100 万件のリストに関数値で `map` を 2 回、関数値の呼び出し 600 万回、うち 300 万回は毎回クロージャを作る） | 67.3 ms | 30.7 ms | 247.8 ms |
| 実行ファイルの大きさ | 113,664 バイト | 5,632 バイト | — |

- **速度**: この測定では Rust の約 2.2 倍速く、JIT の約 8 倍です。ただし比較相手の Rust は、YuiLang の関数型と同じ
  「どのクロージャでも入る型」（`Box<dyn Fn>`）で書いたものです。Rust は確保のたびに OS のヒープを呼びますが、
  こちらは小さいブロック専用の確保器を使うので、その差が出ています。Rust でクロージャの型を固定する書き方
  （`impl Fn`）をすれば確保が起きないので、Rust のほうが速くなります。

入れたもの:

- **関数値の持ち方**: `[参照カウント][本体の機械語の番地][解放の手順の番地][捕まえた値...]` のブロック。
  捕まえた値は、クロージャを作るときにブロックへ写します（値として捕まえる、という言語の規則どおり）。
- **呼び出し**: 本体は、ブロックを第 1 引数として受け取ります。捕まえた値はブロックから借りて読みます。
- **名前で渡した関数**: `xs.map(double)` の `double` は、「引数を 1 つずらして本来の関数へ飛ぶ」短い機械語を挟んで、
  クロージャと同じ形の値にします。
- **`map` などへの受け渡し**: その場に書いたクロージャは、これまでどおりループの本体として展開します（呼び出しなし）。
  名前・変数・関数の戻り値で渡した場合と、本体に `?` や `return` があるクロージャは、要素ごとに呼び出します。
  後者では `?` がクロージャから抜けるという意味が、そのまま保たれます。
- **関数型の解釈**: `fn(Int, String) -> Bool uses io` のような型を扱います。効果（`uses`）は値の持ち方に影響しません。

制限: 関数値の引数は 3 個まで（通常の関数は 4 個まで）。

## 16. 要素への代入と、複製を避ける最適化（2026-11-26、Windows x64）

別に試作した小さなコンパイラ（符号なし 32 ビット整数と、番地を指定したメモリ操作だけの言語。以下「試作版」）と
比べたところ、配列を書き換える処理で `yui run` が 5〜7 倍遅く、`--native` は `flags[i] = 0` に未対応で
コンパイルできませんでした。その差を埋めるために入れたものです。

| 処理（大きい版） | `--native` | 試作版 | `yui run`（JIT） |
| --- | --- | --- | --- |
| Sieve（5,000 までの素数を 2 万回数える） | 205 ms | 138 ms | 2,112 ms |
| Permute（6 要素の順列を再帰で 3,000 回） | 113 ms | 52 ms | 4,307 ms |
| fannkuch-redux（10 要素） | 191 ms | 274 ms | 1,955 ms |

元の比較と同じ小さい版（128 回、32 回、8 要素を 2 回）では、3 本とも 4〜7 ms で、ほぼプロセスの起動時間です
（`--native` 4.8 / 4.5 / 6.6 ms、試作版 4.5 / 3.8 / 7.4 ms、`yui run` 17.8 / 49.3 / 35.3 ms）。

- `--native` は `yui run` の 10〜38 倍速くなりました。
- 試作版との比較では、fannkuch は上回り、Sieve は約 1.5 倍、Permute は約 2.2 倍の時間がかかります。
  条件は同じではありません。YuiLang は 64 ビットで、足し算のたびに溢れを、添字のたびに範囲を検査し、
  リストは値として扱います（共有されていれば複製する）。試作版は 32 ビットの折り返し演算で、
  固定番地のメモリを直接読み書きします。

入れたもの:

- **要素・フィールドへの代入**: `xs[i] = v`、`p.x = v`、入れ子（`rows[i][j] = v`、`board.cells[i] = v`）。
  値は共有されないので、途中のリストや構造体にほかの持ち主がいれば、そこだけ複製してから書きます。
  `xs[i] = v`（要素が整数など）は、持ち主が 1 人ならその場で書くだけの短い機械語になります。
- **最後の使用なら渡すだけにする**: 次の 2 つの形では、参照カウントを増やさずに持ち主を移します。
  移した先で持ち主が 1 人になるので、複製が起きません。
  - `let mut w = v`（関数本体の直下で、`v` がその後使われない場合）。引数は書き換えられないので、
    「引数を受け取って書き換えて返す」関数はこの形で始まります。
  - `x = f(.., x, ..)`（`x` を引数に 1 回だけ渡し、結果を `x` に入れ直す場合）。
- **フィールド越しの読み出し**: `st.v[i]` や `p.items.len()` は、途中の値の参照カウントを触らずに読みます。

Permute は、この 2 つの最適化を入れる前は 491 ms でした（呼び出しのたびに構造体とリストを複製していたため）。

残っている差の候補: ループの中で変わらない検査（持ち主が 1 人か、添字が範囲内か）をループの外へ出すこと、
短い関数のインライン展開、入れ子の代入で途中の値をレジスタに置くこと。

## 17. 代入の速い経路と、追加の前の容量確保（2026-11-26、Windows x64）

16 節の続きです。時間の内訳を測ってから、効くところだけを直しました。

| 処理（大きい版） | 16 節 | 今回 | 試作版 |
| --- | --- | --- | --- |
| Sieve | 205 ms | 193 ms | 140 ms |
| Permute | 113 ms | 76 ms | 52 ms |
| fannkuch-redux | 191 ms | 188 ms | 268 ms |
| リストのベンチマーク（10 節以降と同じもの。Rust は 21.7 ms） | 22.3 ms | 17.8 ms | — |

- **構造体越しの代入の速い経路**: `p.x = v` と `state.cells[i] = v` のように、フィールドだけをたどって届く場所への
  整数などの代入は、途中の値がすべてこの変数だけのものなら、数命令でその場に書きます。
  どれかが共有されていた場合だけ、関数の外に置いた処理で複製してからやり直します。
  16 節では `xs[i] = v` だけが速い経路でした。
- **追加の前の容量確保**: `for i in a..b { xs = xs.push(e) }` のように、追加だけをするループは回数が分かるので、
  ループの前に 1 回だけ容量を広げます。伸ばすたびのメモリの取り直しとコピーがなくなります。
  リストのベンチマークはこれで Rust（`Vec::new()` に `push` する書き方）を下回りました。

Sieve の内訳（2 万回分）は、リストを作る 58 ms、読む 48 ms、書く 約 100 ms で、1 操作あたり 0.4〜0.6 ナノ秒でした。
残っている差は、足し算ごとの溢れの検査、添字ごとの範囲の検査、書き込みごとの「持ち主が 1 人か」の検査です。
ループの中で結果が変わらない検査を外へ出すには、ループの中で変数が何をされるかの解析が要るので、まだ入れていません。

## 18. 段階 5 の前半: 契約、値の表示と比較、ほか（2026-11-26、Windows x64）

`examples/` のうち、`main` のあるもの 10 本中 6 本（`calls`、`division`、`hello`、`integers`、`memo`、`structs`）が
ネイティブでコンパイルでき、`yui run` と同じ出力になります（前回までは `hello` だけ）。
残りは `lists`（`join`）、`generics`（ジェネリックな関数）、`collections`（`Map`）、`tour`（`Float`）です。

入れたもの:

- **`main` から届く関数だけを機械語にする**: テストだけが使う関数は実行ファイルに入らず、対応している必要もありません。
- **契約（`requires` / `ensures`）**: 違反したときの表示は、`yui run` と同じく呼び出した側の位置を指します。
  どこから呼ばれるかは実行時にしか分からないので、契約のある関数を呼ぶ側が「自分の位置を示す文面」の番地を渡します
  （レジスタ 1 個に番地を入れるだけ。契約のない関数を名前で呼ぶ場合は何もしません）。
  `ensures` は、どの `return` から抜けても通る共通の出口で確かめます。
- **引数が 5 個以上の関数**: 5 個目からは呼び出し側のスタックで渡します（Windows の呼び出し規約どおり）。
- **`Int` のメソッド**: `abs`、`min`、`max`、`bit_and` / `bit_or` / `bit_xor`、`shl` / `shr`（範囲外と溢れのエラーつき）。
- **値の表示**: リスト・構造体・列挙を、文字列の中（`"{p}"`）や `to_string()` で `yui run` と同じ形にします
  （`Point { x: 3, y: -4 }`、`[Some([1, 2]), None]`、中の文字列は引用符つき）。
- **値の比較**: リスト・構造体・列挙どうしの `==` / `!=` を、中身を順に比べる形で行います。
- **リストの `first` / `last`**。

表示と比較の機械語は、解放の機械語と同じく、使われた型についてだけ生成します。

まだ対応していないもの: ジェネリックな関数、`Map`、`Float`、`assert`、`panic`、`join` / `sort` / `reverse` /
`contains` / `concat` / `slice` などのリストのメソッド、`trim` / `split` / `to_int` などの文字列のメソッド、
`to_char`、関数値の引数 4 個以上、ファイル入出力とコマンドライン引数。

## 19. 段階 5 の後半: ジェネリックな関数、Map、残りのメソッド（2026-11-26、Windows x64）

`examples/` の `main` のあるもの 10 本中 9 本が、ネイティブで `yui run` と同じ出力になります。
残りは `tour` で、`Float` を使うためです。

入れたもの:

- **ジェネリックな関数**: 使われた型の組み合わせごとに、別の関数として機械語にします（`id<Int>` と `id<String>` は別物）。
  どの型で使われたかは、型チェッカが呼び出しごとに渡します。ジェネリックな関数の中から別のジェネリックな関数を呼ぶ場合も、
  外側の型引数を当てはめてから実体を決めます。
- **Map**: キーは `Int` / `String` / `Bool`。`[参照カウント][件数][容量]` のあとに `[キー][値]` をキーの昇順で並べ、二分探索で引きます。
  `Map { .. }`、`m[k]`、`m[k] = v`、`get` / `has` / `set` / `remove` / `keys` / `values` / `len` / `is_empty`、表示、`==`。
  値として扱うので、共有されている Map を書き換えるときは複製します。部品は `runtime.yui` に YuiLang で書いてあります。
- **リストのメソッド**: `is_empty`、`concat`、`reverse`、`sort`（`Int` と `String`、ヒープソート）、`join`、`contains`（`Int` / `Bool` / `String`）。
- **文字列のメソッド**: `split`、`chars`、`to_lower` / `to_upper`。
  `to_lower` / `to_upper` は a〜z と A〜Z だけを変換します。ASCII 以外の文字を含む文字列に使うと、
  `yui run` と違う結果を黙って出す代わりに、その旨を表示して止まります。

`Map` を使うベンチマーク（40 万回の `counts[key] = counts.get(key).unwrap_or(0) + 1`、キーは 5,003 種類）は、
`--native` 61 ms、Rust 17 ms、`yui run` 89 ms です。`m.get(k).unwrap_or(d)` は `Some` の入れ物を作らずに値を直接読みますが、
1 回の更新で二分探索を 2 回行う（読むときと書くとき）のが残っています。

まだ対応していないもの: `Float`、`assert`、`panic`、リストの `slice`、文字列の `trim` / `replace` / `slice` / `codes` / `to_int`、
`to_char`、関数値の引数 4 個以上、ファイル入出力、コマンドライン引数、`read_line`、複数ファイル（`import`）。

## 20. Float（2026-11-26、Windows x64）

`Float` を入れました。これで `examples/` の `main` のあるもの 10 本すべてが、ネイティブで `yui run` と同じ出力になります
（設計の段階 5 の終了条件）。

| | Rust | `--native` | `yui run`（JIT） |
| --- | --- | --- | --- |
| 小数のベンチマーク（5,000 万回の足し算・掛け算・平方根・割り算） | 48 ms | 102 ms | 3,200 ms |

- **速度**: `yui run` の約 31 倍ですが、Rust の約 2.1 倍です。小数を整数と同じレジスタに置き、
  演算のたびに小数用のレジスタへ移して戻しているためで、小数用のレジスタに置いたままにすれば縮まります。

入れたもの:

- **持ち方**: 64 ビットの小数の中身を、そのまま 8 バイトの値として持ちます。
- **演算と比較**: `+` `-` `*` `/` `%`、単項の `-`、比較。`NaN` との比較は `!=` 以外すべて偽、0 で割れば無限大、という
  プロセッサの規則がそのまま言語の挙動です（`yui run` も同じ）。
- **メソッド**: `to_int`（変換できない値はエラー）、`abs`、`sqrt`、`floor`、`ceil`、`round`（半分は 0 から遠いほうへ）、
  `min` / `max`、`Int` の `to_float`。
- **表示**: 設計の 9 節で危険な点に挙げていた部分です。「その値に戻せるいちばん短い桁数」を、
  大きな整数（32 ビット × 80 マス）の計算で厳密に求めます（Steele と White、Burger と Dybvig の方法）。
  部品は `runtime.yui` に YuiLang で約 200 行で書いてあり、表を持たないので実行ファイルは小さいままです。
  速くはありませんが（1 個の表示に数千回の掛け算）、結果は正確です。

表示の確かめ方: 最小・最大の小数、2 の累乗の境目、`0.1 + 0.2`、`NaN`、無限大、`-0.0` に加えて、
疑似乱数で作った 2,400 個の値（比、非常に小さい値、非常に大きい値、平方根）を表示し、
すべて `yui run`（Rust の標準ライブラリの表示）と一致することを突き合わせテストで確認しています。

まだ対応していないもの: 文字列の `to_float`（文字列から小数への変換）、小数のリストの `sort`、`assert`、`panic`、
リストの `slice`、文字列の `trim` / `replace` / `slice` / `codes` / `to_int`、`to_char`、関数値の引数 4 個以上、
ファイル入出力、コマンドライン引数、`read_line`、複数ファイル（`import`）。

## 21. 残りの機能: 入出力、複数ファイル、`assert`、ほか（2026-11-26、Windows x64）

言語と標準の機能のうち、ネイティブでまだ使えないのは、文字列から小数への変換（`to_float`）、
小数のリストの `sort`、ASCII 以外の文字を含む文字列への `to_lower` / `to_upper` の 3 つになりました。

入れたもの:

- **入出力**: `read_line`、`args`、`read_file`、`write_file`。ファイル名や引数は UTF-8 と UTF-16 を相互に変換し、
  失敗したときの文面（OS が返す説明と番号、中身が UTF-8 でない場合の説明）も `yui run` と同じです。
  コマンドライン引数の区切り方（引用符とバックスラッシュの規則）は Windows の標準に合わせてあります。
- **OS の関数を YuiLang から呼ぶ仕組み**: この機械語は OS と同じ呼び出し規約なので、OS の関数は
  「取り込み表へ飛ぶだけの 1 命令」を挟めば、普通の関数として呼べます。実行時部品（`runtime.yui`）の中では
  `__os_CreateFileW(...)` のように書け、入出力の部品はすべて YuiLang です。使わない関数の分は実行ファイルに入りません。
- **複数ファイル（`import`）**: 取り込んだファイルの中で起きたエラーも、そのファイルの位置を指します。
- **`assert`**: 比較の形なら、失敗したときに両辺の値を表示します（`yui run` と同じ文面）。
- **`panic`**。
- **文字列**: `trim`（Unicode の空白）、`replace`、`slice`（文字単位）、`to_int`、`codes`、`Int` の `to_char`。
- **リスト**: `slice`。
- **関数値の引数の数の制限をなくした**（クロージャは何個でも。名前で渡す関数だけは 3 個まで）。
- **実行時に組み立てるエラー文**: 値を含むエラー（`assert` の両辺、`slice` の範囲、`panic` の文面）は、
  固定の文面と値を順に書き出す共通の仕組みで表示します。

確かめ方: `cargo test` に、引数・標準入力・作業用フォルダを与えて `yui run` とネイティブの両方を動かす
テストを足しました（14 本目）。日本語のファイル名、空の引数、行末に改行のない入力、存在しないファイル、
UTF-8 でないファイルを含みます。

注意点: 端末から直接キーボードで入力する場合、`yui run` は入力を UTF-8 に直して受け取りますが、
ネイティブ版は端末の文字コードのまま受け取ります。ファイルやパイプからの入力では差はありません。

## 22. 段階 7: `yui build` の既定をネイティブに（2026-11-26）

`yui build` は、まず機械語への変換を試し、できないときだけ従来の方式（`yui` 自身にプログラムを同梱）に切り替えます。

| 場合 | 結果 |
| --- | --- |
| Windows x64 で、対応している機能だけを使うプログラム | 機械語の実行ファイル（数 KB〜十数 KB） |
| Windows x64 で、未対応の機能を使うプログラム | 理由を 1 行表示して、同梱方式（約 1.3 MB） |
| Linux、macOS | 同梱方式 |
| `--native` を付けた場合 | 機械語にできなければエラー（何も書き出さない） |
| `--bundle` を付けた場合 | 常に同梱方式 |

- **2 つの方式の挙動をそろえた**: これまでネイティブ版は `yui run` に合わせて、エラーの最後に `1 error(s)` を出していました。
  同梱方式の実行ファイルはこの行を出さないので、どちらの方式でビルドされたかで表示が変わらないよう、ネイティブ側を合わせました。
- **突き合わせの相手を変えた**: `cargo test` は、`tests/native/` の全プログラムを両方の方式でビルドし、
  出力・エラーの文面・終了コードが一致することを確かめます（これまでは `yui run` と比べていました）。
  未対応の機能を使うプログラムが、理由の表示つきで同梱方式になり、正しく動くことも確かめます。
- **型の受け渡し**: 型チェッカがすべての式の型を渡すのは、機械語への変換を試すとき（`yui build` で `--bundle` を付けていないとき）だけです。
  `yui check` / `yui run` / `yui test` の時間は変わりません。

`yui` 本体は、ネイティブコンパイラを含むようになった分、段階 2 の時点の約 0.9 MB から約 1.3 MB に増えています。

設計で残っているのは、段階 6（Linux と macOS 向けの実行ファイル出力）です。

## 23. 速度: 結果の再利用、割り切れるかの判定（2026-11-26、Windows x64）

| | Rust | これまで | 今回 |
| --- | --- | --- | --- |
| `fib(38)` | 58 ms | 162 ms | 3.2 ms |
| 整数ループ 3 億回（`i % 3 == 0` の判定と `i % 7` を含む） | 142 ms | 263 ms | 208 ms |
| 小数のベンチマーク | 49 ms | 102 ms | 104 ms |

- **結果の再利用**: 副作用のない関数（`uses` のない関数）は、同じ引数なら必ず同じ結果になります。
  引数も結果も `Int` で、1 回の呼び出しの中で自分を 2 回以上呼ぶ関数について、計算済みの結果を 1,024 件まで覚えて使い回します。
  `yui run` の JIT が持っていた仕組みで、条件も同じです。Rust は関数に副作用がないことを知らないので、自動ではこれを行えません。
  表は実行ファイルの書き込み可能な領域（ファイル上の大きさは 0）に置くので、`fib` の実行ファイルは 2,560 バイトのままです。
- **割り切れるかの判定**: `x % 定数 == 0`（と `!= 0`）は、割り算も掛け戻しも使いません。
  定数が 2 の累乗なら下位ビットを調べるだけ、奇数なら「その数の逆数（掛けると 1 に戻る数）を掛けて、範囲に入るか」で判定します。
  奇数の方法が正しいことは、単体テストで境目の値と乱数 26 万通りについて、通常の剰余と突き合わせています。
- **数のメソッドを呼び出し扱いしない**: `sqrt` / `abs` / `min` / `max` などは数命令に展開されるので、
  その前後で計算途中の値を退避する必要はありません（これまでは関数呼び出しと同じ扱いで退避していました）。
- **左辺が変数の演算**: `a + b` で `a` が変数なら、いったん別のレジスタへ写さずにその場から使います。

小数が変わっていない理由: 小数の値を整数と同じレジスタに置いていて、演算のたびに小数用のレジスタへ移して戻します。
ループをまたいで使う値（合計など）では、この往復が 1 回ごとの待ち時間になります。
小数の変数を小数用のレジスタに置く変更が要り、今回は入れていません。

試して取り下げたもの: ループの先頭を 16 バイト境界に揃える対応。fannkuch は 205 → 196 ms、Sieve は 184 → 197 ms と
効果が打ち消し合いました。このあたりの 5〜10% の差は、機械語がたまたまどこに置かれたかで変わる範囲です。
「左辺が変数の演算」も同じで、Sieve では速く、fannkuch では遅く出ます（命令数は減っています）。

## 24. ウィンドウ・入力・時刻・乱数（2026-11-26、Windows）

絵の出るプログラム（ゲーム）を作れるように、組み込み関数を 15 個足しました（一覧は SPEC.md）。
`yui run` と `yui build` の両方で同じように動きます。

- **描き方**: ウィンドウは「点の表」を 1 枚持ち、プログラムはそこに色を書き込みます。`window_update()` を呼ぶと、
  その表を拡大して画面に写します。グラフィックカードの機能は使いません。
- **`yui run` 側**: `src/window.rs`。OS の関数を Rust から直接呼びます（外部クレートなし）。
- **`yui build` 側**: `runtime.yui` に YuiLang で書いてあります。ウィンドウに届く出来事の処理は OS の標準のものにまかせ、
  閉じられたかどうかは毎回ウィンドウの有無を調べて知ります（OS から呼び返してもらう関数を用意しなくて済みます）。
  実行時部品が呼び出しをまたいで値を持てるよう、書き込み可能な領域にマスを用意しました（`__global`）。
- **取り込む DLL を必要な分だけに**: 画面まわりの関数は kernel32 ではなく user32 と gdi32 にあります。
  実行ファイルの取り込み表を複数の DLL に対応させ、実際に呼んでいる関数だけを載せるようにしました。
  ウィンドウを使わないプログラムは、これまでどおり kernel32 だけを読み込みます（`hello` は 3,584 バイトのまま）。
- **乱数**: `random_seed` で種を決めると、`yui run` と `yui build` で同じ並びになります（同じ計算を両方に書いてあります）。

確かめ方: 乱数・色・時刻・「ウィンドウがないときの描画と入力」は、突き合わせテスト（`tests/native/random.yui`）に入っています。
ウィンドウを開く部分は自動テストに入れていません。`games/` の 2 本を、引数でコマ数を指定して両方の方式で動かし、
終了時の表示（コマ数と位置）が一致すること、ウィンドウの中身を画像に取って絵が出ていることを手元で確認しました。

大きさと速さ: `games/blocks.yui`（横から見たブロックの世界）は 45 KB の実行ファイルになります。
1 コマあたり 1,200 マスを描き、1 コマごとに 16 ミリ秒待つ作りで、300 コマにかかる時間は `yui run` もネイティブも約 5.2 秒
（1 秒に約 58 コマ）でした。待ちを外すと、1 コマの計算と描画は `yui run` で約 0.4 ミリ秒、ネイティブで約 0.8 ミリ秒です。
ネイティブのほうが遅いのは、塗りつぶしを YuiLang で 1 点ずつ書いているためです（`yui run` 側は Rust のまとめて塗る処理）。
どちらも 16 ミリ秒に対して十分小さいので、いまは直していません。

途中で分かったこと: ネイティブ版は最初、1 秒に約 35 コマしか出ませんでした。OS の `Sleep` は 16 ミリ秒を頼んでも
約 31 ミリ秒待つことがあるためで、精度の高いタイマーを使う待ち方に変えて解消しました。

まだないもの: 文字を描く関数、画像の読み込み、音、キーを「押した瞬間」だけ知る方法（いまは「押されているか」だけ）、
ウィンドウの大きさの変更、Windows 以外。

## 25. 使ってみる: 3 次元のブロックの世界（2026-11-26、Windows x64）

24 節の関数だけを使って、3 次元のブロックの世界（`games/blocks3d.yui`、約 330 行）を YuiLang で書きました。
言語を「使う側」から確かめるのが目的です。

- **描き方**: 画面の点 1 つずつ視線を飛ばし、マスの境目を 1 つずつまたぎながら最初に当たるブロックを探します。
  当たった面の向きで明るさを変え、遠いものは空の色に近づけます。グラフィックカードは使いません。
- **速さ（320 × 200 の点、1 コマに 64,000 本の視線）**: ネイティブ版は 1 コマ約 4.4 ミリ秒で、
  8 ミリ秒の待ちを入れて 1 秒に約 76 コマです。`yui run` は 1 コマ約 170 ミリ秒（1 秒に約 6 コマ）で、遊ぶには遅すぎます。
  小数の計算が中心の処理で、ネイティブは `yui run` の約 40 倍でした。
- **大きさ**: 実行ファイルは 63 KB です。
- **同じ結果になるか**: 引数でコマ数を指定して自動で動かしたとき、終了時の位置（小数）が `yui run` とネイティブで一致します。

書いてみて分かったこと:

- **一度で通った**: 型検査・ビルドとも最初の版で通り、絵も最初から正しく出ました。
- **足りなかったもの**: 三角関数（`sin` / `cos`）が無いので、ゲームの中で級数を使って書いています。標準に入れるべきものです。
  マウスで向きを変える方法（マウスの移動量を知り、カーソルを中央に戻す）も無いので、向きは矢印キーで変えます。
- **書きにくかったところ**: 当たったブロックについて「マスの番号・面・距離」の 3 つを返したいが、
  点ごとに構造体を作ると確保が増えるので、1 つの整数に詰めて返しています。
  小さな構造体を確保なしで返せれば（14 節に挙げた改善）、素直に書けます。
- **速度は問題にならなかった**: 小数は Rust の約 2 倍の時間がかかるままですが、この用途では余裕がありました。

## 26. GPU で描く（2026-11-26、Windows x64）

25 節の描き方（点 1 つずつ計算）は、かかる時間が点の数に比例します。320 × 200 で 1 コマ約 4.4 ミリ秒なので、
1920 × 1080 では計算上 1 コマ 140 ミリ秒ほどになり、滑らかには動きません。
そこで、三角形をグラフィックカード（GPU）に渡して描く組み込み関数を 8 個足しました（一覧は SPEC.md）。

- **使うもの**: OpenGL の古い方式（1.1）。Windows に最初から入っている `opengl32.dll` だけで動き、
  どの操作も「関数を 1 つ呼ぶ」形なので、24 節で作った「OS の関数を呼ぶ仕組み」にそのまま乗ります。
  三角形は「表示リスト」として GPU の側に覚えさせ、毎コマは「その番号を描け」と頼むだけです。
- **`yui run` 側**: `src/window.rs`。`opengl32` の関数を Rust から直接呼びます（外部クレートなし）。
- **`yui build` 側**: `runtime.yui` に YuiLang で書いてあります。足したのは次の 2 点だけです。
  - **小数の渡し方**: Windows の呼び出し規約では、小数の引数は小数用のレジスタ（xmm0〜3）で渡します。
    小数を受け取る OS の関数（6 個、`FLOAT_CALLS`）へ跳ぶ直前に、最初の 4 つの引数をそこへ写す命令を 4 つ入れました。
    5 つ目以降はスタックに置くので、整数と同じ扱いで済みます。
  - **実行時部品では小数の計算をしない**: 必要な小数（画面の大きさ、色の成分など）は、整数から 64 ビット・32 ビットの
    並びを直接組み立てます。視野は整数だけで決めた大きな値で設定してから全体を縮める、という形にして、割り算を避けました。
    点の座標は、YuiLang の小数のリストの中身（64 ビットの小数が並んでいる）の番地をそのまま渡します。写しは作りません。
- **取り込む DLL**: GPU の関数を呼ばないプログラムは `opengl32.dll` を読み込みません（24 節の仕組みのまま）。
- **画面の点と絵の点を 1 対 1 に**: 表示の拡大率が 100 % でない画面では、OS がウィンドウを引き伸ばしてぼやけます。
  `gpu_open` は、引き伸ばさない設定にしてからウィンドウを作ります。

見本として、25 節の世界を GPU で描く版（`games/blocks_gpu.yui`、約 590 行）を書きました。
見えている面だけを三角形にし、横 16 × 奥行き 16 マスの区画ごとに 1 つのまとまりにして、
ブロックが変わったらその区画だけ作り直します。狙いを付ける視線の計算は 25 節と同じものを 1 本だけ使います。

実測（世界は 128 × 32 × 128 マスで 25 節の 16 倍の広さ、木は 220 本）:

| | 25 節（点ごとに計算、320 × 200） | GPU 版（1280 × 720） | GPU 版（1920 × 1080） |
| --- | --- | --- | --- |
| 1 コマの時間 | 約 4.4 ミリ秒（待ちを入れて 1 秒に約 76 コマ） | 16.6 ミリ秒（1 秒に 60 コマ） | 16.6 ミリ秒（1 秒に 60 コマ） |
| そのうち CPU を使った時間 | 約 4.4 ミリ秒 | 約 1.3 ミリ秒 | 約 1.7 ミリ秒 |
| 実行ファイル | 63 KB | 84 KB | 同じ |

GPU 版の 16.6 ミリ秒は、画面の書き換え（1 秒に 60 回）を待っている時間で、これが上限です。
待ちを外したときの速さは測っていません（外す関数を用意していないため）。CPU を使った時間は、600 コマ動かしたときの
プロセス全体の CPU 時間をコマ数で割ったもので、世界を作る時間も含みます。
最初に 64 区画ぶんの三角形を作る時間は、ネイティブで 16 ミリ秒、`yui run` で約 100 ミリ秒でした。
`yui run` でも 1 秒に 60 コマ出ます（重い部分が GPU に移ったため）。

確かめ方: GPU のウィンドウがないときの動き（何もしない、番号は 0）は突き合わせテスト（`tests/native/gpu.yui`）に入っています。
ウィンドウを開く部分は自動テストに入れていません。見本を両方の方式で自動で動かし、終了時の表示が一致すること、
画面を画像に取って同じ絵が出ていること（重ねた長方形の色が指定どおりの値であること）を手元で確認しました。
メモリの解放漏れの検査（`YUI_NATIVE_CHECK_HEAP`）も通っています。キーボードとマウスで実際に遊ぶ確認は、していません。

書いてみて分かったこと:

- **リストを関数に渡して足してもらう書き方は `yui run` で遅い**: 最初は「点のリストを受け取り、面 1 つぶんを足して返す」関数に
  しましたが、`yui run` では呼ぶたびにリスト全体の写しができ、64 区画を作るのに 5.6 秒かかりました（ネイティブは 16 ミリ秒）。
  「面 1 つぶんの短いリストを返す関数」と「その場で 1 つずつ足すループ」に分けて、約 100 ミリ秒になりました。
  ネイティブ版にある「最後の使用なら写さず渡す」最適化が、`yui run` の側には無いためです。
- **整数だけのリストは `yui run` では別の持ち方をしている**ので、色のリストを読む側で両方の形を扱う必要がありました
  （最初は見落として、`yui run` でだけ何も描かれませんでした）。

まだないもの: 絵（模様）を面に貼ること、文字、光の当たり方の計算、マウスで向きを変える方法、
ウィンドウの大きさの変更と全画面表示、画面の書き換えを待たない設定、Windows 以外。

## 27. 通信、文字、AI の仲間（2026-11-27、Windows x64）

「AI と一緒に遊べるゲーム」を、ほかの言語や道具を使わず YuiLang だけで作れるようにしました。
足した組み込み関数は 6 個です（`http_start` `http_done` `http_result` `env` `gpu_text` `text_input`。一覧は SPEC.md）。
副作用の種類に `net` を足しました。

- **通信は裏で進む**: 言語モデルの返事には数秒から数十秒かかるので、待つ間にゲームが止まらない形にしました。
  `http_start` で始め、毎コマ `http_done` で調べ、終わったら `http_result` で受け取ります。
  - `yui run` 側（`src/net.rs`）: 依頼ごとにスレッドを 1 つ作り、OS の通信機能（WinHTTP）を順番に呼びます。
  - `yui build` 側（`runtime.yui`）: スレッドは作らず、WinHTTP の「終わったら知らせる」方式を使います。
    OS は 1 段階終わるごとに、こちらが渡した関数を別のスレッドから呼びます。その関数だけは YuiLang では書けないので、
    native.rs が 45 バイトの機械語として出します。やることは「何が終わったか」を依頼ごとの置き場に書くだけで、
    メモリの確保もほかの関数の呼び出しもしません。続きの段階（返事を待つ、本文を読む）は、`http_done` が
    その書き込みを見て、プログラム本来のスレッドから頼みます。暗号化（HTTPS）は OS がやります。
- **文字の表示**: OS の書体から文字 1 つずつの絵を作って GPU に覚えさせ、並べて描きます（初めて使う文字だけ、その場で作る）。
  日本語もそのまま描けます。1 ビットの絵なので、縁はなめらかではありません。
- **文字の入力**: ウィンドウに届く「文字が打たれた」という知らせを `window_update` がためておき、`text_input` で受け取ります。
  日本語入力で確定した文字も同じ道で届きます。
- **取り込む DLL**: 通信を使わないプログラムは `winhttp.dll` を読み込みません（24 節の仕組みのまま）。

その上に、YuiLang で 3 つ書きました。

- `games/json.yui`（約 360 行）: JSON を読む・書く。値は、自分自身を含む列挙型（`Value`）で表します。
- `games/claude.yui`（約 120 行）: Claude の API を呼ぶ。返事の形を JSON スキーマで決めて送り、返事から本文を取り出します。
- `games/blocks_ai.yui`（約 800 行）: 26 節の世界に、仲間の「ユイ」を足したもの。お願いの文と決まりごとを送ると、
  「何を言うか・何を何個集めるか・どんな箱を並べて建てるか」が JSON で返ってきます。
  ゲームの側は、それをブロック 1 つずつの作業に直し（建てる場所は、プレイヤーの前でいちばん平らな所を探す）、
  ユイがその場所まで飛んでいって 1 つずつ壊したり置いたりします。
  建物は「箱の並び」で受け取ります（後の箱が前の箱を上書きし、`air` の箱でくり抜く）。ブロックを 1 つずつ並べてもらうより、
  返事がずっと短くて済みます。

確かめ方と、確かめていないこと:

- 通信は、公開されている練習用のサーバーに対して、取得（GET）・送信（POST）・日本語を含む見出し・404・存在しない相手・
  行き先として読めない文字列を、両方の方式で試し、結果の文面が一致することを確認しました。
  ネットワークの要らない部分は突き合わせテスト（`tests/native/net.yui`）に入っています。
- JSON と Claude の部品は、付属の `test`（各 3 個）が通り、同じ入力に対してネイティブ版も同じ出力になりました。
- ゲームは、API を呼ばない「決まった返事」で、家を建てる流れと木を集める流れを両方の方式で動かし、
  置いた数・壊した数が一致すること、建った家と文字が画面に出ることを画像で確認しました。解放漏れの検査も通っています。
- **実際の Claude の API は、まだ一度も呼んでいません**（この作業をした環境に API キーが無かったため）。
  送る内容は API の資料どおりに組み立てていますが、通るかどうかは未確認です。
- **キーボードで実際に文字を打つこと（日本語入力を含む）は、確かめていません。**

実行ファイルの大きさ: `blocks_ai` は 254 KB です（26 節の版の 86 KB から増えたのは、主に JSON の部品と、型ごとに作られる処理の分）。

書いてみて分かったこと:

- **自分自身を含む列挙型と Map が、ネイティブ版でそのまま動いた**: JSON の値（`List<Value>` と `Map<String, Value>` を持つ `Value`）は、
  最初の版で `yui run` と同じ結果になり、解放漏れもありませんでした。
- **整数を受け取る組み込みで、文字列用の解放をしてしまう誤り**が 1 つありました（`http_result` を `read_file` と同じ処理に
  乗せたとき、番号を文字列として解放しようとして落ちた）。引数の型を見て分けるように直しました。
- **文字列の中に `"` や `{` を書くのが大変**: JSON を文字列で組み立てると `\"` と `\{` だらけになります。
  JSON スキーマのような決まった文は、読みやすく書ける方法（そのまま書ける文字列など）が欲しくなりました。
- **画面を画像に取る確認で、別のウィンドウが写り込んだ**: 画面の一部を写す方法だと、手前に別のウィンドウがあるとそれが写ります。
  ウィンドウの中身だけを取る方法に変えました。

## 28. 使ってみて足りなかったものを言語に入れる（2026-11-27）

24〜27 節でゲームを書いてみて、YuiLang で書きにくかった所を直しました。どれも、書いていた私（AI）が実際に何度も引っかかった所です。

- **そのまま書ける文字列**（`"""..."""`）: JSON を文字列で書くと `\"` と `\{` だらけになり、読めなくなりました。
  `"""` で囲んだ中は、エスケープも補間もなく、書いたとおりの文字になります。コードに合わせて字下げできるよう、
  閉じる `"""` の前の空白を各行から取り除きます。ゲームの中の Claude への指示（50 行）は、
  引用符つきの行の並びから、ふつうの文章になりました。
- **補間の中の文字列**: `"{names.join(", ")}"` はコンパイルエラーでした。この制限に、ゲームを書く間に 6 回以上引っかかったので、
  外しました（補間の式の中の文字列と文字リテラルを、字句解析が読み飛ばすようにした）。
- **標準の部品**（`import std.math`、`import std.json`）: 三角関数がなく、ゲームごとに級数を書いていました。
  `std.` で始まるモジュールは `yui` 本体に入っていて、ファイルを置かなくても使えます。中身は YuiLang で書いてあるので、
  組み込み関数と違って、`yui run` と `yui build` に同じものを 2 回実装する必要がなく、結果が食い違うこともありません。
  - `std.math` の精度: 2,001 点ずつ Python の結果と比べ、いちばん大きな相対誤差は sin・cos・exp が 2.2 × 10⁻¹⁶、
    ln が 3.2 × 10⁻¹⁶、atan が 3.8 × 10⁻¹⁶、atan2 が 5.1 × 10⁻¹⁶ でした（小数の最後の 1〜2 ビットの違い）。
    同じ 2,001 行の出力は、`yui run` とネイティブ版で 1 文字も違いません。
- YuiLang で書いた字句解析器（`selfhost/lexer.yui`）にも同じ変更を入れ、Rust 版と同じトークン列になることを、
  リポジトリの全ファイル（今回から `std` と `games` も）で確かめています。
